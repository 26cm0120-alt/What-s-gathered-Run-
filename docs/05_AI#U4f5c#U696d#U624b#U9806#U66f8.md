## 1. この手順書について

### 1.1 目的

Claudeが使えないときに、ほかのAIを使っても、開発規約(`01_開発規約`)を守って、安全に作業できるようにする。プログラミングやGitが初心者の人でも、上から順に進めれば、作業が完了できる形にしている。

### 1.2 読み方

- `【 】` で囲んだ部分は、「ここを実際の名前に置き換える」という印である。**`【 】` ごと入力してはいけない。**
- 黒い枠(コードの枠)の中の1行が、1つのコマンドである。1行ずつ、ターミナルに貼り付けて、Enterを押す。
- コマンドの `git --no-pager` は、表示が途中で止まらないようにするための書き方である。
- この手順書と開発規約が食い違った場合は、**開発規約が優先**である。

### 1.3 大原則(5つ)

1. 仕様書に書いてないことを、AIの判断だけで追加させない。
2. AIが出したコードは「未検証」である。Xcodeでビルドして、動作を確認するまで、正式なコードではない。
3. 変更は小さな単位で行う(1機能・1変更)。
4. `main` ブランチには、直接書き込まない。作業用のブランチで作業し、プルリクエストで統合する。
5. 迷ったら、作業を止めて、チームに相談する。

## 2. 全体の流れ

```text
① 準備 → ② AIへ依頼 → ③ 受け取って確認 → ④ ビルドと動作確認
      → ⑤ GitHubへ保存 → ⑥ プルリクエスト → ⑦ 確認して統合
```

| 段階 | やること | 詳しい説明 |
|---|---|---|
| ① 準備 | 最新のコードを取り込み、作業用のブランチを作る | 第4章 |
| ② AIへ依頼 | 資料を渡し、依頼文を書く | 第5章 |
| ③ 受け取って確認 | AIの答えを読み、コードを差し替える | 第6章 |
| ④ ビルドと動作確認 | Xcodeでビルドし、動きを確かめる | 第7章 |
| ⑤ GitHubへ保存 | コミットして、プッシュする | 第9章 |
| ⑥⑦ プルリクエスト | 確認してもらい、`main` へ統合する | 第10章 |

うまくいかないときは、第8章(戻し方)と第11・12章(エラーの対処)を見る。

## 3. 用語(やさしい説明)

| 用語 | 意味 |
|---|---|
| リポジトリ | プロジェクト一式と、その変更の記録を入れた箱 |
| GitHub | リポジトリをインターネット上に置いて、3人で共有する場所 |
| ローカル | 自分のMacの中にある、リポジトリのコピー |
| ブランチ | 作業用の枝。`main` に影響を与えずに、変更を試せる |
| `main` | 「正式に採用したコード」を置く、いちばん大事なブランチ |
| コミット | 変更を、メッセージ付きで、自分のMacに記録すること |
| プッシュ | 自分のMacの記録を、GitHubへ送ること |
| プル | GitHubにある最新の記録を、自分のMacへ取り込むこと |
| プルリクエスト | 「この変更を `main` に入れてください」というお願い。ここで確認してもらう |
| マージ(統合) | ブランチの変更を、`main` に取り込むこと |
| コンフリクト | 同じ場所を別々に変更して、食い違いが起きた状態 |
| ビルド | Xcodeでプログラムを組み立てて、エラーがないか確かめること |

## 4. 作業の前にやること(毎回)

### 4.1 ターミナルを開く

1. 「ターミナル」アプリを開く。
2. 次のように入力する。`cd` のあとに、半角スペースを1つ入れる。

   ```text
   cd 
   ```

3. Finderで、**`Map.xcodeproj` があるフォルダ**(プロジェクトのルート)を、ターミナルの画面へドラッグする。場所が自動で入力される。
4. Enterを押す。
5. 次を実行して、一覧に `Map.xcodeproj` が見えれば、場所は正しい。

   ```text
   ls
   ```

### 4.2 最新のコードにする

```text
git switch main
git --no-pager pull
```

「Already up to date.」と出るか、ファイルの更新が表示されれば、成功である。

### 4.3 手元がきれいか確認する

```text
git --no-pager status
```

「nothing to commit, working tree clean」と出れば、きれいである。それ以外(変更が残っている)の場合は、前の作業が終わっていない。**勝手に捨てず**、コミットするか、チームに相談する。

### 4.4 作業用のブランチを作る

```text
git switch -c 【ブランチ名】
```

- ブランチ名は、半角の英数字とハイフンで、作業の内容が分かる名前にする。
- 新しい機能なら `feature/` を、不具合の修正なら `fix/` を、頭に付ける。
- 例: `feature/start-screen`、`fix/3d-render-update`

### 4.5 作業の前に、ビルドが通ることを確認する

Xcodeで、`Command + B` を押す。「Build Succeeded」と出ることを確認する。

**作業前に失敗していると、AIの変更が原因か分からなくなる。** 失敗するときは、AIに依頼する前に、原因を調べる。

## 5. AIへの依頼の仕方

### 5.1 AIを使うときの心構え

- どのAIを使っても構わない。ただし、**AIは間違える**。Xcodeでのビルドと、動作確認が、最終的な判定である。
- 会話が長くなると、AIは、最初に渡した仕様を忘れやすい。**作業ごとに、新しい会話を始める**のがよい。
- 使えるAIの制限(回数や文字数)で、途中で止まることがある。そのときは、新しい会話で、5.3の「最初の文」から、やり直す。

### 5.2 AIに渡す資料

| 資料 | 何のために渡すか | いつ渡すか |
|---|---|---|
| `docs/01_開発規約.md` | AIが守るルール | 毎回 |
| `docs/02_ゲーム仕様書.md` | ゲームの仕様 | 毎回 |
| `docs/04_UI仕様書.md` | 画面の仕様 | 画面(UI)に関する作業のとき |
| `docs/03_開発ロードマップ.md` | 今どのフェーズか | 必要なとき |
| 変更したいソースファイルの全文 | 変更の対象 | 毎回 |
| 関係するソースファイルの全文 | 型や関数の名前を、AIに正しく知らせる | 毎回(下の注意を参照) |
| エラーのメッセージ、スクリーンショット | 不具合の説明 | 不具合のとき |

**関係するソースファイルを渡すのが大事である。** 変更する部分が、ほかのファイルの型や関数を使っているとき、その定義を知らないAIは、名前を推測して、エラーの原因になる。

**渡し方**
- ファイルを添付できるAIは、`.md` や `.swift` を添付する。
- 添付できないAIは、ファイルの中身を全文、貼り付ける。
- 長くて一度に入らないときは、「資料を3回に分けて送ります。全部送り終わるまで、返事は『受け取りました』だけにしてください」と最初に伝えてから、分けて送る。

### 5.3 最初に貼る文(コピーして使う)

新しい会話を始めたら、資料を渡す前に、次の文をそのまま貼り付ける。

```text
あなたは、Swift/SwiftUIのiOSアプリ開発を手伝うAIです。以下のルールを必ず守ってください。

【プロジェクト】
「Dungeon Game」。ファミコン時代のWizardryのような、グリッド型の3Dダンジョン探索ゲームです。
開発環境はXcode(Swift、SwiftUI)。3人(A・B・C)が、GitHubを使って共同開発しています。
私は初心者です。専門用語には、短い説明を付けてください。

【最優先のルール】
1. 渡した仕様書・開発規約を最優先にする。仕様に書かれていないことを、あなたの判断だけで追加しない。仕様の矛盾や不明点があれば、実装せずに、私へ質問する。
2. 私が指定したファイルだけを変更する。ほかのファイルは変更しない。
3. 必要な箇所だけ変更し、無関係なコードを書き換えない。
4. コードのコメントは日本語で書く。既存のコメントは、変更しない部分では消さずに残し、処理を変更した部分は、コメントも合わせて更新する。
5. 1回の依頼では、1つの機能・1つの変更だけを行う。
6. あなたが出したコードは「未検証」です。「コンパイルできます」と断言しない。私がXcodeでビルドして確認します。

【出力の形式】
- 最初に、変更するファイルの一覧と、変更の概要を書く。
- 変更したファイルは、ファイルごとに、ファイル名を見出しにして、全文を出す(一部だけを書かない)。
- 変更していないファイルは出さない。
- 最後に、次の形式で報告する。
  【AI変更報告】
  変更ファイル：
  変更内容：
  変更していないファイル：
  影響する機能：
  影響しないことを確認した機能：
- 私が確認すべき動作も、箇条書きで書く。

まず、これから渡す資料を読んで、「読みました」とだけ返してください。
```

そのあとで、5.2の資料を渡す。AIが「読みました」と返したら、5.4の依頼文を送る。

### 5.4 依頼文の書き方

`docs/AI依頼テンプレート.md` の枠を、コピーして、`【 】` の部分を埋める。

**記入例**(トラップのメッセージを変える、小さな依頼)

```text
【プロジェクトの目的】
Dungeon Game(3Dダンジョン探索)。仕様書は渡した資料を参照。仕様にないことを、AIの判断だけで追加しない。

【担当者】
A

【作業対象ファイル】
Map/Events/Trap.swift

【変更してよいファイル】
上記のみ

【変更してはいけないファイル】
上記以外すべて

【現在の動作】
トラップを踏むと、「トラップ! 向きが反転した」と表示される。

【期待する動作】
表示するメッセージを、「罠だ! 向きが反転した」に変える。

【関係する仕様】
02_ゲーム仕様書 §8 T:トラップ

【既存機能への影響】
向きの反転そのものは、変えない。

【完了条件】
メッセージだけが変わり、そのほかの動作は今までと同じ。

必要な箇所だけ変更し、無関係なコードは変更しないこと。
コードのコメントは日本語で書くこと。既存のコメントは、変更しない部分では消さずに残し、処理を変更した部分は、コメントも合わせて更新すること。
変更後は、規約§14の「AI変更報告」の形式で、変更ファイル・変更内容・影響を報告すること。
```

### 5.5 良い依頼と悪い依頼

| | 悪い依頼 | 良い依頼 |
|---|---|---|
| 範囲 | 「スタート画面と面の選択とギブアップを、全部作って」 | 「まず、スタート画面だけ作って」 |
| 対象 | 「いい感じに直して」 | 「`DungeonView.swift` の、左の壁の描画だけ直して」 |
| 不具合 | 「動かない」 | 「前進しても3D表示が変わらない。ビルドは成功する。関係するファイルは次のとおり(全文を貼る)」 |
| 仕様 | 「もっと良くなるように、機能を足して」 | 「仕様書§4.3のとおりに」 |

### 5.6 1回の依頼は小さくする

大きな依頼は、AIが仕様を取り違えたり、多くのファイルを書き換えたりして、原因が分からなくなる。**1つの機能を、いくつかの小さな依頼に分けて、1つずつ、確認しながら進める。**

### 5.7 答えの受け取り方を指定する

依頼文に、次の一文を足すと、貼り付けの間違いが減る。

```text
変更したファイルだけを、ファイル名を見出しにして、全文で出してください。一部だけの書き換え(「この行を〜に変えて」)は、しないでください。
```

初心者が、部分的な書き換えを手作業で行うと、間違えやすいためである。

## 6. AIの答えを受け取ったら

### 6.1 まず読む(コードを貼る前に)

1. **変更するファイルの一覧を見る。** 依頼していないファイルが入っていたら、そのファイルは差し替えない。AIに「依頼していないファイルは、変更しないでください」と伝えて、やり直してもらう。
2. **「AI変更報告」を読む。** 何を変えたのか、何を変えていないのか、確認する。
3. **仕様にないことが足されていないか見る。** (例: 頼んでいないボタン、効果音、機能の追加)

### 6.2 コメントを確認する

- 既存のコメントが、意図なく消えたり、短くなったりしていないか。
- 新しく書かれたコメントが、日本語か。

(開発規約§6.1)

### 6.3 ファイルを差し替える

**方法A:既存のファイルを書き換える**

1. Xcodeの左側で、該当のファイルをクリックして開く。**ファイル名がAIの指定と同じか、必ず確認する。**
2. `Command + A`(全選択)を押す。
3. AIのコード(全文)を貼り付ける(`Command + V`)。
4. `Command + S` で保存する。

**方法B:新しいファイルを追加する**

1. Finderで、AIが指定したフォルダ(例: `Map/Events/`)を開く。
2. テキストエディタなどで、AIが指定した名前の `.swift` ファイルを作り、コードを貼り付けて保存する。
3. Xcode 26では、`Map/` の下のフォルダに入れたファイルは、自動でXcodeの左の一覧に出る。出ないときは、Xcodeを一度閉じて、開き直す。
4. ファイル名は、中に書かれた型の名前と、合わせる(例: `struct TrapEvent` なら `Trap.swift` など、AIの指定に従う)。

### 6.4 何が変わったかを確認する

ターミナルで、次を実行する。

```text
git --no-pager status
```

変更されたファイルの一覧が出る。**意図したファイルだけ**が出ているか確認する。意図していないファイルが出ていたら、第8章の方法で、そのファイルだけ元に戻す。

変更の中身は、次で見られる。

```text
git --no-pager diff
```

行の先頭が `+` の行は追加、`-` の行は削除である。コメントの行が、意図なく `-` で消えていないか、確認する。

## 7. ビルドと動作確認

### 7.1 ビルドする

Xcodeで `Command + B` を押す。「Build Succeeded」と出れば、成功である。

### 7.2 エラーが出たら

エラーの主な例と、対処を示す。

| エラーの例 | 意味 | 対処 |
|---|---|---|
| `Invalid redeclaration of 'X'` | 同じ名前の型やファイルが、2つある | 古いファイルが残っていないか確認して、重複を消す |
| `Cannot find 'X' in scope` | 「X」という名前が見つからない | 必要なファイルが足りないか、AIが別の名前を使っている。エラーと、関係するファイルの全文を、AIへ渡して修正してもらう |
| `Value of type 'X' has no member 'y'` | 「X」に、「y」という機能がない | AIが、存在しない機能を使っている。現在のコード(該当ファイルの全文)を渡して、修正してもらう |
| `Missing argument` や `Extra argument` | 部品に渡す値の数や名前が合わない | 部品を呼び出す側と、定義側の両方のファイルを渡して、修正してもらう |

**AIにエラーを伝えるときの依頼文(例)**

```text
ビルドでエラーが出ました。エラーの内容と、関係するファイルの現在のコード(全文)を貼ります。
原因を説明して、直してください。直すときも、変更するファイルは最小限にして、コメントは残してください。

【エラーの内容】
(Xcodeのエラーメッセージを、文字のままコピーして貼る)

【該当ファイルの現在のコード】
(ファイル名と、全文を貼る)
```

**3回直しても直らないときは、その作業を中止して、元に戻す**(第8章)。同じことを繰り返すと、余計に壊れる。

### 7.3 実行して確認する

`Command + R` でシミュレーターで動かし、次を確認する。

- [ ] 「前進」で、1マス進み、3D表示が変わる
- [ ] 「左旋回」「右旋回」で、向きが変わり、3D表示が変わる
- [ ] 壁の方向には進めない
- [ ] オートマップに、歩いたところだけが表示される
- [ ] プレイヤーの向きが、オートマップの三角形で分かる
- [ ] T(トラップ)を踏むと、向きが反転する
- [ ] K(鍵)を取ると、「鍵を手に入れた」と出る
- [ ] 鍵がないと、G(ゴール)に入れない。鍵があると、ゴールできる
- [ ] 今回の依頼で変えていない部分が、今までどおり動く

### 7.4 確認結果を記録する

確認した項目は、第10章のプルリクエストの「検証状況」に、チェックを入れて残す。実機で確認したときは、それも記録する。

## 8. うまくいかないときに戻す

**注意:** 保存していない変更や、コミットしていない変更は、下の操作で消える。**消える前に、本当に捨てていいか、確認する。**

### 8.1 1つのファイルだけ、元に戻す

```text
git restore 【ファイルのパス】
```

パスは、`git --no-pager status` の表示から、コピーする(例: `Map/Rendering/DungeonView.swift`)。

### 8.2 変更したファイルを、すべて元に戻す

```text
git restore .
```

### 8.3 新しく追加したファイルを消す

`git --no-pager status` で、「Untracked files」(追跡されていないファイル)として出るファイルは、Finderで見つけて、ゴミ箱に入れる。

### 8.4 コミットしたが、`main` にはまだ入れていない作業を、捨てる

```text
git switch main
git branch -D 【ブランチ名】
```

**この操作は、そのブランチの作業を消す。** 実行する前に、必ず相談する。

### 8.5 すでに `main` に統合したものを、取り消す

自分で判断せず、チームに相談する。GitHubのプルリクエストのページにある「Revert」ボタンで、取り消すための新しいプルリクエストを作れる。

## 9. GitHubへ保存する(コミットとプッシュ)

### 9.1 コミットする

1. 変更されたファイルを確認する。

   ```text
   git --no-pager status
   ```

   意図していないファイル(例: `xcuserdata` など、自分の設定のファイル)が入っていないか、確認する。

2. 変更をまとめて、コミットの対象にする。

   ```text
   git add -A
   ```

3. メッセージを付けて、コミットする。

   ```text
   git commit -m "【日本語で、何を変えたか】"
   ```

   メッセージの例:
   - 「スタート画面を追加」
   - 「3D描画: DungeonViewにmapとplayerを直接渡す」
   - 「トラップのメッセージを変更」

### 9.2 プッシュする

```text
git push -u origin 【ブランチ名】
```

2回目以降(同じブランチ)は、次だけでよい。

```text
git push
```

成功すると、「Create a pull request for ...」という案内と、URLが表示される。

**初めてのプッシュで、ログインを求められたとき**
- ユーザー名は、GitHubのユーザー名を入力する。
- パスワードの欄には、GitHubのパスワードではなく、**パーソナルアクセストークン**を入力する。
- トークンは、GitHubの画面で作る。右上のアイコン → Settings → 左の一覧の最下部の Developer settings → Personal access tokens → Tokens (classic) → Generate new token (classic)。「repo」にチェックを入れて作成し、表示された文字列を、その場でコピーする(画面の表示は変わることがある)。
- **トークンは、他の人にも、AIにも見せない。ファイルやコミットにも書かない。**
- うまくいかないときは、Xcodeの設定のアカウントに、GitHubを追加する方法や、無料アプリの「GitHub Desktop」を使う方法もある。

## 10. プルリクエストで確認してもらう

### 10.1 プルリクエストを作る(GitHubの画面)

1. プッシュしたあと、ブラウザでリポジトリのページを開く。
2. 黄色の帯の「Compare & pull request」ボタンを押す。(出ないときは、「Pull requests」タブ → 「New pull request」)
3. タイトルを、日本語で、何を変えたか分かるように書く。
4. 本文に、ひな形が自動で入る。次のとおりに埋める。
   - 変更の概要を書く。
   - **AI変更報告**を、AIの出した内容をもとに書く。**使ったAIの名前も書く。**
   - 関係する仕様を書く(例: 02_ゲーム仕様書 §8)。
   - 検証状況のチェックボックスに、実際に確認した項目だけ、チェックを入れる。
5. 右側の「Reviewers」に、確認する人を選ぶ。
6. 「Create pull request」を押す。

### 10.2 確認する人がすること

1. 「Files changed」のタブで、変更の内容を読む。
2. 次を確認する。
   - 仕様書のとおりか。
   - 依頼していない変更がないか。
   - 既存のコメントが消えていないか。日本語か。
   - 担当外のファイルを、勝手に変更していないか。
3. 問題なければ、「Review changes」→「Approve」→「Submit review」を押す。
4. 問題があれば、コメントを書いて、修正してもらう。

**確認する人が、まだいないとき**(BとCが決まる前など)は、自分で確認して、備考に「レビュー者: 未定(Aのセルフレビュー)」と書く。

### 10.3 統合する

1. 「Merge pull request」を押し、「Confirm merge」を押す。
2. 統合が終わったら、「Delete branch」で、使い終わったブランチを削除してよい。

### 10.4 統合したあと、手元を最新にする

```text
git switch main
git --no-pager pull
```

## 11. 困ったとき(エラーの早見表)

| メッセージ | 意味 | 対処 |
|---|---|---|
| `Repository not found` | URLが違う、または権限がない | `git remote -v` でURLを確認する。GitHubの「Code」ボタンのURLと比べる。招待を承認しているか確認する |
| `fatal: not a git repository` | ターミナルの場所が違う | 4.1をやり直す |
| `Please commit your changes or stash them` | 手元に、コミットしていない変更がある | コミットするか、相談する(勝手に捨てない) |
| `divergent branches` | 手元とGitHubが、別々に進んでいる | 落ち着いて、`git --no-pager status` と `git --no-pager log --oneline -5` の結果を持って、チームに相談する |
| `Updates were rejected`(プッシュ時) | GitHubに、自分の知らない新しい変更がある | `git --no-pager pull` をしてから、もう一度プッシュする |
| `Permission denied` や `403` | 権限がない、またはトークンが違う | 招待を承認しているか確認する。トークンを作り直す |
| `CONFLICT ... Merge conflict in ...` | 同じ場所を別々に変更して、食い違った | 第12章 |
| `detached HEAD` | ブランチの上にいない状態 | 作業を止めて、`git switch main` をして、相談する |

## 12. 食い違い(コンフリクト)が起きたら

### 12.1 状態の見分け方

`git pull` のあと、「CONFLICT」と表示される。食い違ったファイルの中に、次のような印が入る。

```text
<<<<<<< HEAD
(自分の側の内容)
=======
(GitHub側の内容)
>>>>>>> origin/main
```

### 12.2 直す手順

1. **慌てない。**何も強制しない。
2. `git --no-pager status` で、「both modified」と出たファイルを確認する。
3. Xcodeで、そのファイルを開き、`<<<<<<<` から `>>>>>>>` までの、両方の内容を読む。
4. 両方の意図を残す形に直す。分からなければ、印の付いた部分と、その周辺を、AIに貼って「この2つの変更を、両方生かす形にまとめて」と依頼する。
5. 印の行(`<<<<<<<`、`=======`、`>>>>>>>`)を、すべて消す。
6. ビルドして、成功することを確認する。
7. 次を実行する。

   ```text
   git add 【ファイルのパス】
   git commit --no-edit
   git push
   ```

### 12.3 どうしても分からないとき

`git pull` の途中でコンフリクトが起きたなら、次で、`pull` を始める前の状態に戻せる。

```text
git merge --abort
```

戻したあと、チームに相談する。

## 13. やってはいけないこと

- **`main` に、直接プッシュしない。**必ずブランチとプルリクエストを使う。
- **`git push --force`(または `-f`)を使わない。**ほかの人の記録を、消してしまうことがある。
- **トークンやパスワードを、コード・コミット・AIとの会話に、書かない。**
- 担当外のファイルを、勝手に変更しない(担当は `README.md` の表を見る)。
- AIが出したコードを、ビルドや動作確認なしで、`main` に入れない。
- 仕様を、コードから先に変えない。変えるときは、先に仕様書を更新して、チームで確認する。

## 14. Claudeが使えるようになったとき(引き継ぎ)

1. 他のAIで作業した内容は、プルリクエストの「AI変更報告」に、**使ったAIの名前**も書いて、残す。
2. Claudeに戻ったら、まず、最新の `main` を取り込む(4.2)。
3. Claudeには、`docs/` の資料と、直近の変更(`git --no-pager log --oneline -10` の結果と、変更したファイル)を渡して、続きを頼む。
4. 他のAIが出したコードの確認を、Claudeに頼んでもよい(仕様との適合、コメントの消失、不要な変更など)。

## 16. AIに状況を伝えるとき

### 16.1 AIは、GitHubもMacの中も見られない

AIには、GitHubの画面も、自分のMacの中も、見えない。**AIが知っているのは、こちらが会話に貼った内容だけ**である。だから、状況を相談するときは、今の状態を、正確に貼る。古い情報や、うろ覚えで説明すると、AIは間違った案内をする。

### 16.2 貼るもの

ターミナルで、リポジトリのルートから、次を実行して、結果を貼る。

```text
git --no-pager status
git --no-pager log --oneline -10
git --no-pager branch -a
git remote -v
```

| コマンド | 分かること |
|---|---|
| `git --no-pager status` | 今のブランチと、コミットしていない変更 |
| `git --no-pager log --oneline -10` | 直近10件の記録 |
| `git --no-pager branch -a` | 手元とGitHubのブランチの一覧 |
| `git remote -v` | GitHubへの接続先 |

エラーが出たときは、**エラーの文字を、そのままコピーして貼る**。言い換えたり、要約したりしない。

次のものを添えると、さらに正確に伝わる。

- GitHubのプルリクエストのページや、「Files changed」の画面のスクリーンショット
- 確認してほしいファイル(添付、または全文の貼り付け)

### 16.3 貼る前の注意

- **トークン、パスワードが、文字や画面に写っていないか確認する。**写っていたら、その部分を消してから貼る。
- `git log` を、`--oneline` を付けずに実行すると、メールアドレスなどが表示される。貼るときは、`--oneline` を付けた書き方を使う。

### 16.4 状況を伝える依頼文(コピーして使う)

```text
今の状況を貼ります。内容を読んで、次にやることを、初心者向けに、順番に教えてください。
貼った内容に書かれていないことは、「分からない」と答えてください。推測で答えないでください。
危険なコマンド(`git push --force`、`git reset --hard`、`git clean -fd`、`rm -rf` など)は、案内しないでください。

【やろうとしていること】
(例: 作った変更を、GitHubへ送りたい)

【困っていること・エラー】
(エラーの文字を、そのまま貼る)

【git status の結果】
(貼る)

【git log --oneline -10 の結果】
(貼る)

【git branch -a の結果】
(貼る)
```

### 16.5 AIの答えを、そのまま実行しない

- AIは、見えていないGitHubの状況を、推測で「こうなっているはず」と答えることがある。**貼った内容と食い違う説明は、信用しない。**
- 次のコマンドを勧められたら、**実行せずに、チームに相談する。**保存していない変更や、記録を消してしまうことがある。
  - `git push --force`(または `-f`)
  - `git reset --hard`
  - `git clean -fd`
  - `rm -rf`
- 実行する前に、そのコマンドが何をするのか、AIに説明してもらう。説明が分からなければ、実行しない。
